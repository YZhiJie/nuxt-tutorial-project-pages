# 事故响应手册

## 分级

| 级别 | 判定 | 响应 |
| --- | --- | --- |
| P0 | 全站不可用、数据丢失、安全事件 | 立即拉起战情室，10 分钟内同步 |
| P1 | 核心路径不可用或错误率 > 5% | 30 分钟内定位并缓解 |
| P2 | 单模块异常、性能明显下降 | 当日修复或降级 |
| P3 | 体验问题、文案错误 | 进入常规迭代 |

## 处置流程

1. **确认与止损**：确认影响面，必要时关闭功能开关、回滚版本或限流。
2. **建立时间线**：从监控、日志、`x-request-id` 串联请求，记录每个动作的时间。
3. **定位根因**：先看指标（错误率 / P95 / 饱和度），再看日志，最后看发布与配置变更。
4. **恢复验证**：核心路径、登录、写入、缓存一致性逐项验证。
5. **对外沟通**：说明影响、当前状态、下次更新时间；避免猜测根因。
6. **复盘**：24 小时内输出，聚焦系统改进而非个人责任。

## 排障入口

- 请求链路：响应头 `x-request-id` → 服务端日志 `event.context.requestId`。
- 指标：`/api/observability/metrics`（RED 指标、耗时直方图、SLO gauge）。
- 渲染异常：检查 `routeRules` 的缓存策略与 CDN 是否命中旧 HTML。
- 认证异常：区分 401（未登录 / 会话过期）与 403（权限不足）。
- 实时异常：SSE 连接数、重连次数、`Retry-After` 与代理超时。

## 常用降级手段

- 关闭非核心功能开关，保留登录与读写主链路。
- 将个性化页面临时切为 `ssr: false`，降低服务端压力（需评估 SEO 影响）。
- 对写接口启用更严格的限流与排队。
- 静态资源回退到上一版本指纹目录。
