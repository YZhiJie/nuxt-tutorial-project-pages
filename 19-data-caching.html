19. 数据缓存与状态一致性 ​

本章示例：app/composables/useNotesCached.ts、app/pages/notes/admin.vue、app/nuxt.config.ts 运行方式：cd app && npm install && npm run dev，浏览器访问 http://localhost:3000/notes，开两个 tab 验证同步

概念解析 ​

Nuxt 数据缓存的第一性原理是「key 即身份」。useFetch 会根据 URL + 选项自动推导 key，useAsyncData 使用显式 key；任何组件用同一个 key 调用，共享同一份 data 与同一次请求——这就是 dedupe 机制：导航时十个组件同时 useFetch('/api/notes')，实际只发一次请求。useNuxtData(key) 可以只读地拿到这份共享缓存，是跨组件同步状态的最轻方案。选 key 就是设计缓存边界：key 里是否包含查询参数、用户 id，决定了不同场景是共享还是隔离。

getCachedData 把缓存命中策略交给你。默认每次进入页面都会重新请求，getCachedData: (key, nuxtApp) => nuxtApp.payload.data[key] ?? nuxtApp.static.data[key] 可以让数据在「本次会话内只取一次」。进阶写法是结合时间戳自定义 TTL：把 { data, fetchedAt } 存进 useState，getCachedData 里判断新鲜度决定是否复用。这把 useAsyncData 从「每次必请求」升级为「可编程的客户端缓存层」，列表 → 详情 → 返回列表的场景收益最大。

Nitro storage 是服务端缓存的统一抽象。useStorage() 背后是 unstorage，同一套 API 可切换 memory（默认）、redis、cloudflare-kv、fs 等驱动。routeRules 的 isr/swr/cache 本质上也是把渲染结果与响应写进 storage 挂载点（如 cache:、nitro:routes:）。理解这一点就能做两件大事：本地开发用 memory 零依赖，生产切 redis 多实例共享缓存；nuxt.config.ts 里 nitro.storage 声明挂载点，代码里 useStorage('cache').setItem(key, value) 手动管理。

一致性三板斧：invalidateNuxtData、refreshNuxtData、clearNuxtData。refreshNuxtData(key) 重新执行对应 handler 拉新数据；invalidateNuxtData(key) 只标记失效，等下一次被使用时才重新请求（更省）；clearNuxtData(key) 把缓存清回初始态。三者解决的是同一个问题的不同力度：写操作后让哪些数据变成「不可信」。再叠加乐观更新（先改 UI 缓存、失败回滚）与多 tab 同步（BroadcastChannel），就构成完整的前端数据一致性工具箱。

典型应用场景 ​

  • 列表 → 详情往返：getCachedData 让列表数据 5 分钟内免重取，返回列表零等待。
  • 写后失效：新建笔记后 invalidateNuxtData('notes')，下次进列表自动拉新。
  • 多实例部署：Nitro storage 切 redis 驱动，ISR 缓存跨实例共享，扩缩容不丢缓存。
  • 多 tab 会话同步：登录/登出用 BroadcastChannel 广播，所有 tab 的 useState 同步更新。
  • 乐观更新 CRUD：点赞先变红再请求，失败时回滚并 toast，感知延迟为零。
  • 按用户隔离缓存：key 拼接 user:${id}:notes，切换账号时 clearNuxtData() 全清。

完整代码示例 ​

ts
// 文件: app/composables/useNotesCached.ts
import type { Note } from '#shared/types/note'

// 带 TTL 的客户端缓存：5 分钟内重复进入页面不再请求
const TTL = 5 * 60 * 1000

export async function useNotesCached() {
    // 用 useState 记录上次取数时间，跨组件共享
    const fetchedAt = useState<number>('notes:fetched-at', () => 0)

    return await useAsyncData<Note[]>('notes', () => $fetch('/api/notes'), {
        getCachedData(key, nuxtApp) {
            const fresh = Date.now() - fetchedAt.value < TTL
            if (!fresh) return undefined  // 返回 undefined = 缓存未命中，重新请求
            return nuxtApp.payload.data[key] ?? nuxtApp.static.data[key]
        }
    }).then((result) => {
        // 请求成功后刷新时间戳
        if (result.status.value === 'success') fetchedAt.value = Date.now()
        return result
    })
}

运行方式：cd app && npm install && npm run dev，在列表页与详情页都调用 useNotesCached()，DevTools Network 面板观察 5 分钟内往返两个页面只有一次 /api/notes 请求。

ts
// 文件: app/nuxt.config.ts
export default defineNuxtConfig({
    nitro: {
        storage: {
            // 声明 cache 挂载点；本地默认 memory，生产可切 redis
            cache: {
                driver: process.env.REDIS_URL ? 'redis' : 'memory',
                url: process.env.REDIS_URL
            }
        }
    },
    routeRules: {
        // ISR 渲染结果也写入 storage，redis 驱动下多实例共享
        '/notes/**': { isr: 300 }
    },
    compatibilityDate: '2025-07-15'
})

运行方式：默认 memory 驱动直接 npm run dev；设置 REDIS_URL=redis://localhost:6379 后同一缓存可被多个实例共享，用 useStorage('cache') 在 server 路由里读写验证。

vue
<!-- 文件: app/pages/notes/admin.vue -->
<script setup lang="ts">
    import type { Note } from '#shared/types/note'

    const { data: notes, refresh } = await useFetch<Note[]>('/api/notes')
    const toast = useState<string | null>('toast', () => null)

    async function remove(id: number) {
        // 乐观更新：先从共享缓存里移除，UI 立即变化
        const backup = notes.value
        notes.value = (notes.value ?? []).filter((n) => n.id !== id)
        try {
            await $fetch(`/api/notes/${id}`, { method: 'DELETE' })
            // 标记失效而非立即刷新：下次使用时再拉新
            await invalidateNuxtData('notes')
        }
        catch {
            // 失败回滚 + 提示
            notes.value = backup
            toast.value = '删除失败，已恢复'
        }
    }
</script>

<template>
    <main>
        <h1>笔记管理（乐观更新演示）</h1>
        <p v-if="toast" class="toast">{{ toast }}</p>
        <ul>
            <li v-for="note in notes ?? []" :key="note.id">
                {{ note.title }}
                <button type="button" @click="remove(note.id)">删除</button>
            </li>
        </ul>
        <button type="button" @click="refresh()">手动刷新</button>
    </main>
</template>

运行方式：npm run dev 后访问 http://localhost:3000/notes/admin，点删除观察 UI 立即响应；临时把 API 改成抛错可验证回滚路径。

ts
// 文件: app/plugins/broadcast.client.ts
export default defineNuxtPlugin(() => {
    const channel = new BroadcastChannel('nuxt-session')
    // 监听其他 tab 的失效广播，保持多 tab 数据一致
    channel.onmessage = (event: MessageEvent<{ invalidate?: string[] }>) => {
        if (event.data.invalidate) {
            event.data.invalidate.forEach((key) => invalidateNuxtData(key))
        }
    }
    // 暴露广播方法供写操作后调用
    return {
        provide: {
            broadcastInvalidate: (keys: string[]) =>
                channel.postMessage({ invalidate: keys })
        }
    }
})

运行方式：npm run dev 后开两个 tab 访问 http://localhost:3000/notes，在一个 tab 执行写操作并调用 $broadcastInvalidate(['notes'])，另一个 tab 的数据会同步失效。

最佳实践 ​

  1. key 设计先于代码：把「哪些数据共享、哪些隔离」画成 key 的命名规范（如 notes、note:${id}、user:${uid}:notes），团队所有人按规范写，缓存行为才可预测。
  2. 写后优先 invalidate 而非 refresh：失效标记是惰性的，只有真正再次用到才请求；盲目 refresh 可能为用户永远不会再看的页面白白拉数据。
  3. 乐观更新必须配回滚与提示：先改缓存 → 请求 → 失败恢复备份，三步缺一不可；同时给用户 toast，避免「明明删了又出现」的困惑。
  4. storage 驱动按环境分层：本地 memory、预览 fs、生产 redis/kv；用环境变量切换而非改代码，nitro.storage 配置保持单一来源。
  5. 敏感数据别进 payload 与共享缓存：用户私有数据的 key 必须带用户标识，登出时 clearNuxtData() 全量清理，防串号。
  6. 多 tab 只同步「失效信号」：BroadcastChannel 传 key 不传数据本身，让各 tab 各自重新拉取，避免跨 tab 传递大对象的序列化成本与一致性问题。

常见问题 ​

Q：useFetch('/api/notes') 在两个页面各写一次，会请求几次？ ​

A：一次。相同 URL + 选项推导出相同 key，Nuxt 自动 dedupe 并共享 data。但若两边选项不同（如不同的 query），key 就不同，会各自请求——这就是「key 即身份」。

Q：invalidateNuxtData 之后数据为什么没立即更新？ ​

A：这是设计如此：它只把缓存标记为失效，等下一次有组件使用这份数据时才重新请求。想要「立即重新拉取」请用 refreshNuxtData 或该请求的 refresh()。

Q：getCachedData 里返回了旧数据，为什么请求还是发出去了？ ​

A：常见原因是返回了 undefined 以外的 falsy 值被误判，或 payload.data[key] 本身不存在导致走了 static.data 分支也是空。调试时在 getCachedData 里打日志确认返回值，命中时必须是真实数据对象。

Q：多实例部署后 ISR 页面有的新有的旧？ ​

A：默认 memory 驱动是实例内缓存，每个实例各自再生。把 nitro.storage 的对应挂载点切到 redis（或平台 KV），所有实例共享同一份渲染缓存即可解决。

小结 ​

  • key 即身份：同 key 自动共享与 dedupe，useNuxtData(key) 只读访问共享缓存。
  • getCachedData 实现可编程客户端缓存，配合 useState 时间戳可做 TTL。
  • Nitro storage（unstorage）统一服务端缓存，memory/redis/kv 驱动按环境切换。
  • 一致性三板斧：invalidateNuxtData（惰性失效）、refreshNuxtData（立即拉新）、clearNuxtData（清空）。
  • 乐观更新 = 先改缓存 + 失败回滚 + 用户提示；多 tab 用 BroadcastChannel 广播失效信号。

自测题 ​

1. 【基础】`refreshNuxtData`、`invalidateNuxtData`、`clearNuxtData` 三者的语义差异是什么？

refreshNuxtData(key) 立即重新执行 handler 拉取新数据；invalidateNuxtData(key) 只把缓存标记为失效，下次被使用时才重新请求（惰性）；clearNuxtData(key) 直接把 data 清回 undefined/默认值。写操作后一般用 invalidate，用户点了「刷新」按钮用 refresh，登出切账号用 clear。

2. 【进阶】用 `getCachedData` 实现「10 分钟内不重复请求」需要哪几个要素？

三要素：一个跨组件共享的时间戳（useState 记录 fetchedAt）；getCachedData 内比较 Date.now() - fetchedAt < TTL，新鲜则返回 nuxtApp.payload.data[key]（或 static.data），不新鲜返回 undefined 触发重新请求；请求成功后更新时间戳。缺了更新时间戳这一步，缓存会永远停留在第一次取数时刻。

3. 【挑战】为什么多实例部署时必须把 Nitro storage 切到 redis，而不是每个实例各用 memory？

memory 驱动是进程内缓存：实例 A 再生的 ISR 页面，实例 B 完全不知情，负载均衡把用户打到不同实例就会看到新旧不一的内容；扩容/重启还会整体丢缓存。redis 作为外部共享存储，让所有实例读写同一份缓存，渲染结果一致、再生只发生一次，且实例生命周期与缓存解耦。
