# 10. composables 与 Pinia

> 本章示例：`app/composables/useNotes.ts`、`app/stores/counter.ts`、`app/stores/user.ts`、`app/pages/playground.vue`
> 运行方式：`cd app && npm install && npm run dev`，浏览器访问 `http://localhost:3000/playground`

## 概念解析

组合式函数（composable）是把可复用逻辑封装成函数的标准方式。Nuxt 约定 `app/composables/` 目录下的文件自动导入：文件名即函数名（如 `useNotes.ts` 导出 `useNotes`），业务代码里零 import 直接用。自动导入默认扫描顶层文件与子目录的 index 文件，更深层级需在 nuxt.config.ts 的 `imports.dirs` 中登记。命名上统一 use 前缀 camelCase，返回值约定为「响应式状态 + 方法」的对象，便于解构使用。

编写 composable 的黄金法则：内部放心使用 useState、useFetch、useRoute 等 Nuxt API，但这些 API 依赖当前 Nuxt 实例上下文，必须在 setup 同步链路中调用（组件 setup、插件、路由中间件）；在 `await` 之后或事件回调里首次调用会报 "Nuxt instance unavailable"。

Pinia 是 Vue 官方状态管理库。执行 `npm i @pinia/nuxt` 并在 nuxt.config.ts 注册 `modules: ['@pinia/nuxt']` 后开箱即用，store 放在 `app/stores/` 下同样自动导入。`defineStore` 有两种风格：options 风格（state/getters/actions 三段式，结构清晰）与 setup 风格（用 ref/computed 自由组合，TypeScript 推断更佳）。

SSR 下 Pinia 状态由 @pinia/nuxt 模块自动序列化进 payload 并在客户端水合还原，原理与 useState 一致，请求之间互不干扰。注意在 store 里调用 Nuxt API 的边界：setup 风格 store 的同步初始化阶段可用 useFetch；action 常在事件回调中执行，异步请求建议改用 `$fetch`，页面导航交给组件里的 `navigateTo`，不要在 action 深处导航。

## 典型应用场景

- **逻辑复用**：useNotes 封装笔记列表的获取与缓存，多页面共享。
- **简单全局状态**：useCounter 这类轻量场景，composable + useState 即可胜任。
- **复杂业务状态**：用户、权限、购物车等多实体联动，用 Pinia 的 getter/action 组织。
- **派生计算**：Pinia getter（如 double、isAdmin）集中维护派生逻辑。
- **调试追踪**：Pinia 在 Vue DevTools 中有专属面板，便于观察状态变更。

## 完整代码示例

```ts
// 文件: app/composables/useNotes.ts
import type { Note } from '#shared/types/note'

export const useNotes = () => {
    // 列表缓存在 useState 中，跨页面共享且 SSR 安全
    const notes = useState<Note[]>('notes', () => [])
    const keyword = ref('')

    const refresh = async () => {
        // query 支持传入 ref，keyword 变化会触发重新请求
        const { data } = await useFetch<Note[]>('/api/notes', {
            query: { q: keyword }
        })
        notes.value = data.value ?? []
    }

    return { notes, keyword, refresh }
}
```
> 运行方式：自动导入，页面 setup 中直接 `const { notes, refresh } = useNotes()` 即可使用。

```ts
// 文件: app/stores/counter.ts
// options 风格：state / getters / actions 三段式
export const useCounterStore = defineStore('counter', {
    state: () => ({
        count: 0,
        step: 1
    }),
    getters: {
        // 派生状态，缓存自动生效
        double: (state) => state.count * 2
    },
    actions: {
        inc() {
            this.count += this.step
        },
        reset() {
            this.count = 0
        }
    }
})
```
> 运行方式：注册 @pinia/nuxt 后自动导入，组件中 `const store = useCounterStore()` 直接使用。

```ts
// 文件: app/stores/user.ts
// setup 风格：像写组件 setup 一样写 store
export const useUserStore = defineStore('user', () => {
    const user = ref<{ name: string } | null>(null)

    const fetchMe = async () => {
        const { data } = await useFetch('/api/auth/me')
        user.value = data.value?.user ?? null
    }

    const logout = async () => {
        // action 内处于事件回调链路，用 $fetch 而非 useFetch
        await $fetch('/api/auth/logout', { method: 'POST' })
        user.value = null
    }

    return { user, fetchMe, logout }
})
```
> 运行方式：登录后调用 `useUserStore().fetchMe()`，user 状态在 SSR 水合后全站共享。

```vue
<!-- 文件: app/pages/playground.vue -->
<script setup lang="ts">
// composable 与 store 均为自动导入
const { count, inc, dec, reset } = useCounter()

const counterStore = useCounterStore()
// storeToRefs 解构 state/getters，保持响应式
const { count: storeCount, double } = storeToRefs(counterStore)
// actions 无响应式，可直接解构
const { inc: storeInc, reset: storeReset } = counterStore
</script>

<template>
    <main>
        <section>
            <h2>useCounter（composable）</h2>
            <p>{{ count }}</p>
            <button @click="inc">+1</button>
            <button @click="dec">-1</button>
            <button @click="reset">清零</button>
        </section>
        <section>
            <h2>Pinia counter store</h2>
            <p>{{ storeCount }}，双倍：{{ double }}</p>
            <button @click="storeInc">+{{ counterStore.step }}</button>
            <button @click="storeReset">清零</button>
        </section>
        <!-- 同页再挂一个使用同一 store 的组件，验证状态同步 -->
        <CounterBox />
    </main>
</template>
```
> 运行方式：访问 `http://localhost:3000/playground`，对比两种方案的响应式表现与状态同步。

## 最佳实践

1. **可复用逻辑优先抽 composable**——符合组合式思想，也便于测试与按需引入。
2. **useXxx 只在 setup 同步链路调用**——await 之后改用已取出的值，避免丢失 Nuxt 上下文。
3. **轻量用 useState，复杂用 Pinia**——别为两个值引入 store，也别用裸 ref 堆出「面条状态」。
4. **解构 store 用 storeToRefs**——直接解构 state/getters 会丢响应式；actions 可直接解构。
5. **store action 里用 $fetch**——useFetch 依赖 setup 上下文，action 常在事件回调中执行。
6. **导航放组件，不放 store**——action 里 navigateTo 易触发上下文告警，也让 store 更难复用。

## 常见问题

### Q：composables 子目录里的文件为什么不生效？

A：自动导入默认只扫顶层文件与子目录的 index 文件；深层文件需在 nuxt.config.ts 配置 `imports: { dirs: ['composables/**'] }`。

### Q：为什么报 "Nuxt instance is unavailable"？

A：在 await 之后或定时器回调里首次调用了 useFetch/useState 等 API。把调用提到 setup 同步阶段，或在延迟执行的函数里改用 $fetch。

### Q：options 风格与 setup 风格怎么选？

A：团队偏传统、追求结构统一选 options；需要灵活组合 composable、更好的 TS 推断选 setup。二者可在同一项目混用。

### Q：解构 store 后数据不更新了？

A：state 与 getters 需用 `storeToRefs(store)` 解构才能保持响应式；只有 actions 能直接解构。

## 小结

- `app/composables/` 自动导入，use 前缀命名，返回「状态 + 方法」对象。
- composable 内部可用 useState/useFetch，但必须处于 setup 同步链路。
- Pinia 经 `@pinia/nuxt` 接入，`app/stores/` 自动导入，defineStore 支持 options 与 setup 两种风格。
- `storeToRefs` 保持解构响应式；SSR 下 store 状态随 payload 水合还原。
- action 里用 `$fetch`，导航留给页面组件。

<details>
<summary><b>1. 为什么 useFetch 不能在 await 之后的回调里首次调用？</b></summary>

这类 API 依赖当前 Nuxt 实例上下文，跨过异步边界后上下文不再可用，会报 "Nuxt instance unavailable"；应在 setup 同步阶段建立调用，或改用 $fetch。

</details>

<details>
<summary><b>2. storeToRefs 的作用是什么？</b></summary>

它把 store 的 state 与 getters 转成 ref 集合，解构后仍保持响应式；直接解构得到的是普通值，store 更新时视图不会刷新。

</details>

<details>
<summary><b>3. useState 与 Pinia 如何取舍？</b></summary>

少量、松散的全局值用 useState 即可；多实体、含派生计算与业务流程的复杂状态用 Pinia，还能获得 DevTools 支持；两者在同一项目可共存。

</details>
